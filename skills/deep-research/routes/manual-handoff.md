# Handoff when browser access is blocked

Use only for a concrete access or capture blocker. Explain which product and step failed, what remains possible, and the smallest action needed from the user. Keep other independent selected work moving where possible. Do not substitute ordinary chat, web search or an API for a browser Deep Research job.

## Before submission

Save the exact common brief in `PROMPT.md` and the access problem in `RUN.md`. If browser setup cannot be completed, offer to have the user open the selected product, choose Deep Research, and submit that exact brief once. Manual handoff is a fallback, not the normal installation path. Ask for the resulting task URL and record it before monitoring or export resumes. Keep project/notebook filing separate from research status.

## After submission or an uncertain Send

Give the user the existing task URL, or the last known tab and submission time if no URL was captured. Ask them to locate or inspect that job, not to paste the prompt again. Record `submission-unknown` until resolved. Never treat a missing chat in the Deep Research container as proof that no job exists.

## Capture only

If research finished but export is blocked, ask the user to export the **existing report** using its native download control. For Gemini, use Export to Docs and download the complete Doc. Identify the destination and have the user supply the export or saved path. Resume the normal identity, completeness and source-list checks; don't accept a pasted excerpt as a full report. Preserve the original and record user-assisted capture.

## Resume and cleanup

Keep task URLs, state, blockers and any downloaded files in the project archive. On “resume,” inspect those records first. Do not relaunch completed or unresolved jobs. Keep blocked tabs and Gemini Docs available until capture is verified; then apply the host adapter's cleanup behavior. Never claim handoff, export, filing or cleanup succeeded until observed.
