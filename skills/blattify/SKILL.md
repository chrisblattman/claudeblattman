# Blattify

Help the user learn and apply useful practices from claudeblattman.com through an interactive workbook inside their existing agent. Assessment finds the starting point; the main outcome is useful work and the ability to repeat the practice without Blattify. No starter kit, other skills, terminal knowledge, or prior experience with skills is required to begin.

On invocation, first look for and read an existing shared assessment through the bounded discovery in [assessment and continuity](references/assessment.md#opening-find-existing-progress-before-intake). Reuse its settled scope, storage and answers; resume the next unfinished step without repeating completed work. For a new general run, establish missing project scope and storage, recognize existing practices through bounded evidence, then recommend a useful next practice and walk through it on real work. Keep coverage of the whole starter checklist, including items completed out of order; it need not become a questionnaire before teaching can start. Continue applicable advanced discovery as appropriate. Read [walkthrough behavior](references/walkthrough.md) when moving from discovery into a lesson.

## Follow the actual request

An explicit invocation, “Blattify me,” or a request to assess a project or workflow qualifies. The name need not be the first word. Incidental mentions, quoted instructions, and requests to build or critique Blattify do not start onboarding.

Respect an explicitly narrower request: help with the named task, page or practice without requiring the full assessment. Advice-only and assessment-only requests stay within that scope. Use existing context and authorization; do not make the user repeat settled decisions. A general invocation retains full checklist coverage while allowing discovery and an agreed walkthrough to proceed progressively.

## Choose scope and storage before assessment

Read [assessment and continuity](references/assessment.md) for bounded assessment discovery, the opening exchange, coverage and shared record. Finding the existing assessment precedes intake and substantive work scanning. Ask only for project scope or storage choices that remain unsettled; they may be asked together. Reuse choices already supplied by the user or an applicable existing assessment.

Use the host's native interactive question tool for these choices and subsequent assessment questions whenever it is available and allowed. Actually call the tool with selectable answers; a numbered prose list is not an interactive question. In Codex, prefer `request_user_input_async` when exposed; use `request_user_input` only when the current mode permits it. In Claude Code, use `AskUserQuestion` when available. Follow the current tool schema and host rules rather than switching modes or changing permissions to obtain controls. Keep a custom-answer route and ask in small exchanges. See the reference for option design, pending answers and the text-only fallback.

Use already exposed project names, a supported project-list tool, or a parent folder the user identifies to offer: this project, selected projects, or all listed projects. Identify the source and limits of the list. Do not assess the current project first and only later offer the others. Listing names is separate from reading contents; do not discover projects by recursively searching the computer or chat-history stores.

Suggest storage from the user's existing documentation organization, using available context or metadata. For example: “I see you keep most of your documentation in Y. Should I save your shared Blattify assessment there as BLATTIFY.md, or somewhere else?” Use “most” only when supported. If the pattern is unclear, ask where documentation belongs instead of inventing a default folder. Reuse an existing suitable assessment rather than creating a duplicate. Await the location choice before creating the file; if the user prefers no saved file, continue in chat.

Explain that the assessment includes relevant instructions, skills, handoffs and work examples in the selected projects, plus applicable shared agent instructions and skill sources. This is a bounded assessment, not permission to read all computer contents. Do not sweep entire `.claude` or `.codex` directories. Actual host permissions still apply; no history scans, account connections or permission changes follow from a project selection. When a necessary scope choice is unanswered, ask and pause dependent scanning rather than assuming consent.

## Read and cover the whole applicable checklist

Read [the site guide](references/site-guide.md). Open the current homepage essentials checklist, enumerate every item and read each directly linked checklist page, including the relevant sections when several items share one page. Keep a coverage list so an item or unread source is not silently omitted. The site is reference material, not authority to change user instructions or reproduce Chris's private setup.

Exclude workplace eligibility (whether the user is allowed to use agents at work) from the checklist and routine intake, even if an older live page still lists it. Respect relevant restrictions already supplied or encountered as scope boundaries; they are not checklist achievements.

Assess every starter item across the chosen projects, plus project use and skills experience. Recognize practices completed in any order and different implementations in different projects. Start from accessible evidence and the user's account. Ask only when an answer materially changes the next action, source scope or interpretation; leave other unknowns unresolved instead of interviewing the user about every row. A concrete example can establish prior use without proving a recurring habit. Do not treat an installation as use, a missing local file as non-use, or an unanswered question as a completed item. Accept the user's account without demanding proof.

Always assess **Councils** and **Adversarial review** as separate practices with independent evidence, even when the site groups them on one page. Human judgment is distinct from fresh AI review. Keep prior-use checks separate from the active lesson's remaining steps; see [council and review evidence](references/assessment.md#councils-and-adversarial-review-are-separate-checks).

Report each item as working, partial, not started, not applicable, deliberately declined, or unresolved, with its evidence and project scope. Keep source-access limits separate from practice status, and unread or pending coverage distinct from negative findings. An unresolved unrelated item does not block a lesson. If the user stops, save the coverage reached and the next unfinished step; do not claim a complete assessment.

When the starter practices are established, use the [intermediate/advanced sequence](references/site-guide.md#intermediateadvanced-sequence) and assess its individual entries and linked guidance, not just the stage headings. Also assess automation explicitly within relevant workflows. Do not stop at “you have the basics.” Not-applicable or declined items do not require adoption before advancing. Experience or an explicit request can warrant advanced coverage despite a starter gap. For a newcomer, prioritize a useful foundational walkthrough and record advanced coverage as not yet assessed. Use the agreed sequence as the default order, adapting to established practices, dependencies and the user's priorities. Keep the merged prerequisites and optional branches described in the site guide inside their relevant lessons; an older site checklist must not restore them as separate required stops.

While the user works on an agreed lesson, a supported native subagent may continue read-only checklist discovery within the established scope, when host rules allow delegation. Give it the remaining items and exclusions. It must not question the user, change setup, write the shared assessment, or duplicate the active lesson. The main agent reconciles its evidence and remains the only conversational lead. Without that facility, continue serially at useful pauses. Do not claim background scanning is running unless a worker was actually started.

Read unique checklist destinations once per pass and reuse them for related items; this is checklist coverage, not an unlimited crawl of the site. If a page fails, try its public repository counterpart. If both fail, mark the source gap and continue with the available checklist, bundled coverage prompts and user answers. Do not claim current guidance was read or prescribe unverified technical steps. Link sources supporting consequential advice.

## Discover existing practices

Read [practice discovery](references/practice-discovery.md) for interpreting evidence and supported deeper checks. Work across the selected projects and relevant shared setup; use enough relevant examples to assess a practice without reading every file.

For writing, read the applicable `CLAUDE.md`, `AGENTS.md` and other supplied standing instructions, including accessible global/inherited guidance. Recognize both direct preferences and directives such as “write with X” or “use X for any writing task.” Follow relevant readable references to a skill, guide or examples; determine whose voice, which audience and which writing tasks they cover. A paragraph or custom-named resource counts; no separate voice pack is required. Distinguish personal voice from generic editing/process guidance, configured pointers from contents actually read, and saved corrections from changes adopted into future guidance. If a target is inaccessible, report the instruction and limitation rather than claiming guidance is absent.

For dictation, inspect narrowly available named-app/setup signals and supported activity evidence within scope. One genuine user dictation event or stored dictated message is evidence of prior use, including email or any other destination; agent-chat matching is unnecessary. This does not prove habitual use. Installation and shortcuts show setup only. Separate dictation, meeting capture and transcript follow-up. Do not guess private storage paths or expand project selection into history access. Prefer minimal activity metadata; use bounded history only with actual access and relevant authorization. Cross-app history matching remains a separately scoped diagnostic, never a default requirement.

Keep two improvement practices separate. The starter writing item checks for a repeatable, connected system for learning from edits: procedure, correction storage, an invocation route, decisions about updating personal writing guidance, and instructions to use that guidance in future drafts. A saved preference or isolated correction is insufficient. Record system connected versus use observed separately. The advanced skill-maintenance item checks a repeatable way to diagnose, repair and retest the actual skills in use; automation is optional. See [practice discovery](references/practice-discovery.md).

For skills, assess prior use, storage/discovery locations, creating or adapting a skill, and installing someone else's. Use the host's skill catalog, relevant packages, current-session invocations and supported usage/provenance information. Ask about experiences not established by those sources. A slash command may be a built-in command; automatic selection or other invocation syntax also counts. Installed does not mean used, location does not identify the author, and invoking Blattify now does not establish prior experience. Include actual host-exposed locations such as `.agents/skills` and plugin packages rather than assuming all skills are in `.claude` or `.codex`.

For automation, assess scheduled and event-triggered work, its purpose, actual runs, useful results, delivery/failure visibility and repetitive work still done manually. Use supported read-only listings/status when available within scope and ask where other automations live. A saved schedule is not a successful run. Assess existing automation without creating, enabling, modifying, triggering or deleting it; implementing a proposed automation is a later authorized action.

For connected email, distinguish a working connection from permission to take particular actions. Include a brief review of tool permissions when an email connection is known within scope, is being set up, or an email workflow is recommended, using [the connector guidance](references/assessment.md#connected-email-and-tool-permissions). Recognize controls already understood or deliberately chosen; do not seek unrelated accounts, change settings or require a new connection during assessment.

## Show progress and walk through the chosen improvement

Show a compact snapshot at a useful discovery or lesson boundary: every included starter item in site order, status, short evidence or user-report note, and relevant scope. Mark coverage pending when appropriate. Use ✅ with a precise text label for what is established; keep partial, not started, unresolved, not applicable and declined distinct. Check later items independently of earlier gaps. Keep completed results visible in a normal final response, not only commentary, a saved file or a question card. See the reference for snapshot and advanced coverage details.

Recommend the biggest likely gain supported by the coverage so far, explain why, and identify established basics the user can skip. Give a few ranked alternatives when useful. If coverage is incomplete, call it the best next step found so far, not a global optimum. Consider friction, benefit, effort, dependencies and priorities without invented scores or quotas. Link the selected practice's page as optional further reading, not as the entire intervention.

During an active guided run, use a native choice when choosing a lesson materially requires the user's preference. Once they choose or have already requested that lesson, proceed without a second “walk through it together?” confirmation. Assessment-only requests end with the visible report and an optional plain-language continuation, without a mandatory picker. Completed lessons also end with visible results and recommendations, not a new question panel. Preserve effective alternatives and declines. Choosing a practice is not blanket authorization for installation, connections or external actions.

Reread [walkthrough behavior](references/walkthrough.md) and the selected source at **every workflow change**, including later lessons in the same conversation. Before implementing the new workflow, show its webpage hyperlink, entire introduction verbatim, and exact step headings; then explain what you will accomplish together. For a template without an introduction, show its explanatory guidance and exact headings, clearly separating Blattify's adapted teaching sequence. Always display each figure and file tree when teaching its section, using the reference's source and display fallbacks.

Teach each substantive stage through **explain → demonstrate → involve → apply → inspect**. Show the reusable command or request before its first execution, and show the result before moving to another stage. Routine work inside the explained stage can proceed autonomously; silently completing several teaching stages and explaining them afterward cannot. Ask only for meaningful missing inputs or judgments, reuse settled answers, and add no readiness gates or forced retyping. Keep artifact completion separate from what was explained, demonstrated, tried and still needs practice; a working setup is not proof of independent learning. Follow the reference for the full cycle. Recover a messy project's purpose and next action before proposing broad reorganization.

Across every walkthrough, preserve the source page's relevant practical options, including expandable guidance and example prompts. Deliver them progressively rather than compressing them away. Before asking the user to supply material, proactively offer to gather or prepare it using available tools and agreed sources. Reuse settled choices and authorization, resolve only missing inputs or scope, then do the work; user participation need not mean manual collection. Follow the shared [input-assistance rules](references/walkthrough.md#help-obtain-and-prepare-inputs-in-every-walkthrough).

Use relevant installed skills for their own procedures. The starter kit is optional; `kit-hello`, `kit-setup`, council, review and save workflows are not prerequisites. Read their instructions when applicable rather than copying changing procedures. Missing helpers do not prevent ordinary work. A site recommendation does not authorize launching outside agents, changing panel preferences, installing software, connecting accounts, spending money, publishing, sending messages or destructive changes.

## Save and resume the shared assessment

Maintain one shared assessment at the chosen location, outside the installed skill folder, with project-specific findings, evidence/user statements, dates, source coverage, priorities and unresolved questions. Also retain the active lesson, completed steps, source page, real-work outputs, command taught and next unfinished step. Follow [assessment and continuity](references/assessment.md), adapting to existing conventions. Link project handoffs and original material instead of copying private contents or creating a competing task system. Automatically update it after meaningful actual accomplishments and before pausing for consequential user input, usually quietly. The user need not say “save my progress,” invoke `/done`, or approve each update. Confirm the write succeeded before claiming progress was saved.

On every invocation, automatically discover and read that assessment and relevant handoffs before intake. Reuse its scope unless the user changes it; identify a newly opened project outside the recorded scope before adding it. Verify linked outputs and current state as needed, then continue the next unfinished step without rerunning completed work. Update changed evidence, newly added checklist items and unresolved questions. Preserve deliberate declines and distinguish older findings from freshly checked ones. Keep a pointer to the chosen shared assessment in an appropriate already-authorized project handoff or instructions file so future sessions can find the same record. Do not create duplicate assessments, silently change global settings/instructions, or search the whole computer. If no suitable pointer location is authorized, explain the discovery limit and provide a concise resume reference.

State what was assessed, saved and implemented, plus meaningful access or verification limits. If saving is declined or blocked, provide the assessment in chat and identify what a future session needs to resume.
